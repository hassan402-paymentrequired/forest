# School Portal — Module Plan

## Context

The School portal (`school_users` accounts, sidebar layout, root-level routes) is being built module by module, each one finished end-to-end (migrations → models → relationships → controllers → pages → tests) before the next starts. This doc is the running reference for what modules exist, how they relate, and decisions made about scope — updated as we go, not written once and frozen.

**Build order so far:**
1. ✅ Ministry invite → School accept-invitation → `school_users` login (done)
2. ✅ Teachers (done)
3. ✅ Classes (done — built ahead of Students since Students has a required FK to it)
4. ✅ Students (done — **will be revisited**, see Academic Sessions & Terms below)
5. ✅ Guardians (done)
6. ✅ Academic Sessions & Terms (done — `AcademicSession`/`AcademicTerm` models, `/academic-sessions` + nested `/academic-terms` routes, "Academic Terms" nav page; one `is_current` term per school, flipped via a dedicated mark-current action)
7. ✅ Students: migrated `class_id` to session-scoped `Enrollment` (done — see below)
8. ✅ Attendance (done — see below)
9. ✅ Academics (done — see below)
10. 🔜 **Finance & Expenses** (next)
11. Reports — scope TBD when we get there (see below)
12. Dashboard — last, since it's a summary view over everything else

**Also done, orthogonal to the numbered list above:** the AI Assistant chat UI (see "AI Assistant" section below) — this is the platform-wide conversational assistant from `project_direction.md`, not one of the sequential school-data modules, so it was built alongside rather than slotted into the order.

## AI Assistant — status

**UI: built, ported from `frontend/`. Backend: real `laravel/ai` plumbing, no model configured yet.**

Two surfaces, both real (not mocked), sharing one backend:
- **Docked panel** (`AiSidebar`, shown on every School page except the assistant's own page) — for a School user, a real input that hands off to the full page (optionally carrying the typed draft via a `draft` query param); unchanged "Coming soon" placeholder for Ministry users, since only the School side is wired.
- **Full page** (`/ai/chat`, nav item "Assistant" in the School sidebar) — top-right toolbar (New Chat pencil icon + a History icon opening a `⌘K` command-palette modal) + a real streaming conversation, ported from the `frontend/` (Zola) Next.js app's chat components. The history UI went through two passes: first a plain Dialog list (a deliberate simplification), then replaced with a faithful port of Zola's actual `CommandHistory` (cmdk-based palette: search-to-filter, grouped by Today/Last 7 days/Last 30 days/year, inline rename, inline delete-confirm, `⌘K` shortcut) once it became clear the user wanted that exact component, not an equivalent. `components/ui/command.tsx` (wraps the newly-added `cmdk` package) and `components/chat/{command-history,command-footer,history-utils}.tsx` are the ported pieces; `use-key-shortcut` ported alongside. Dropped from this port: pin/unpin (cosmetic-only even in `frontend/` itself — not persisted there either), the hover-preview panel (`chat-preview-panel.tsx` — needs its own JSON endpoint, a separate follow-up if wanted), and the mobile `vaul`-based `DrawerHistory` (the cmdk dialog is used at every width instead of branching on breakpoint).

**Backend: rebuilt on `laravel/ai` (already installed, `composer.json` had it from the start) instead of hand-rolled models.** First pass wrongly built custom `ChatThread`/`ChatMessage` tables + a fake placeholder-string streamer — corrected once it became clear the point of having `laravel/ai` installed was to use its `Conversation`/`ConversationMessage` models and `RemembersConversations` trait for automatic persistence, not to duplicate them. Current shape:
- `App\Ai\Agents\SchoolAssistant` — the agent (`Agent` + `Conversational`, `Promptable` + `RemembersConversations` traits). Instructions are generic ("You are the assistant for a school administrator...") — no tools yet, since answering from live school data (attendance, grades, enrollment) is a separate, later feature, not part of standing the plumbing up.
- `AiChatController` — `store()` pre-creates an empty `Conversation` row (title `"New chat"`) so "New Chat" always has a stable id to navigate to; `respond()` calls `(new SchoolAssistant)->continue($conversation->id, as: $schoolUser)->stream($content)`, iterates the returned `StreamEvent`s, and echoes just the `TextDelta::$delta` chunks — `RemembersConversations`' `RememberConversation` middleware persists both the user and assistant messages automatically once the stream completes, no manual `->create()` calls needed. A `try`/`catch` around the stream falls back to a friendly "couldn't reach the AI model" string if the call throws (e.g. no provider key configured yet, which is the current state — nothing is configured in `.env`/`config/ai.php` beyond the package's published defaults).
- **Migration fix required:** `laravel/ai`'s published migration (`database/migrations/..._create_agent_conversations_table.php`, now owned by this app) defines `participant_id` as `unsignedBigInteger`, matching Laravel's default auto-increment `users` table. This app's `SchoolUser` uses ULID string primary keys, so that column was changed to `string('participant_id', 36)` in both the conversations and messages tables before migrating — a real incompatibility between the package's default and this app's ID scheme, not a style choice.
- `SchoolUser` gained `use HasConversations;` (from the package) for the `$schoolUser->conversations()` relation.
- `HandleInertiaRequests` shares `auth.school` on every page so the docked panel can tell whether it's looking at a School user without a dedicated request.
- `update()` renames a conversation (`PUT /ai/chat/threads/{thread}`), backing the command-palette's inline rename. Guarded so a title already set by the user is never silently overwritten by `respond()`'s auto-title-from-first-message (checks `title === 'New chat'`, the placeholder, before overwriting).
- Tests use `SchoolAssistant::fake([...])` (the package's own testing support) rather than hitting a real provider.

**Frontend port scope, since a line-for-line port of `frontend/`'s chat components wasn't possible as-is:** `frontend/` is built against Vercel AI SDK v4-era APIs (`@ai-sdk/react`'s old `useChat({api, initialMessages, streamProtocol})`); the versions that actually install today are a much newer, incompatible generation (`ai@7`, `@ai-sdk/react@4` — the two packages' version numbers don't correspond to each other, and v4→v7 restructured messages around `UIMessage.parts` instead of a plain `.content` string). The data/state layer (`use-chat-core.ts` and friends — IndexedDB caching, guest-mode, a client-side chat-store Context) was rewritten from scratch as one small hook (`resources/js/hooks/use-ai-chat.ts`) using the current `@ai-sdk/react`/`TextStreamChatTransport` API, since Inertia already gives page-prop-driven history for free — porting Zola's client-cache layer verbatim would have fought the framework, not matched it. The **visual/presentational layer was ported faithfully**: `components/prompt-kit/*` (message primitives, markdown+shiki code blocks, chat-container/scroll-button via `use-stick-to-bottom`, prompt-input) and `app/components/chat/*` (message bubbles, conversation list) are real ports, adapted off Next.js-only bits (`next/dynamic` → `React.lazy`, `next-themes` → this app's own `useAppearance` hook, `next/image` → plain `<img>`) — not simplified rebuilds. New dependencies added: `@ai-sdk/react`, `ai`, `framer-motion`, `react-markdown`, `remark-gfm`, `remark-breaks`, `marked`, `shiki`, `use-stick-to-bottom`.

**Deliberately dropped, not ported** (confirmed dead/out-of-scope in `frontend/` itself per its own docs, or tied to features this platform doesn't have yet): file/image attachments and the image lightbox, web search + sources + tool-invocation display, reasoning/chain-of-thought display, the quote-a-reply feature, message editing, the model-picker, pin/unpin, the hover-preview panel, and the mobile `vaul` drawer (see above — the `cmdk` command palette itself **was** ported faithfully). `@phosphor-icons/react` was installed then removed again — every icon needed in the pieces actually kept was already available via `lucide-react`, this app's existing icon library.

**Remaining open questions:**
- Configure an actual provider (`config/ai.php` + the relevant `.env` key — Ollama, OpenAI, Anthropic, etc.) — until then, `SchoolAssistant` throws on every real call and the controller's fallback string is all users see. Config-only change once a key exists; no code change.
- Give `SchoolAssistant` tools once it needs to answer from live school data (attendance, grades, enrollment, leave status) — the whole reason `project_direction.md` picked Laravel: tool/function calling against the live DB, not a fine-tuned model.
- Ministry-side wiring — the docked panel still shows "Coming soon" there; extending real chat to Ministry users needs either a polymorphic `participant` (already how `laravel/ai`'s `Conversation` model works, so this may be cheap) or a parallel Ministry-side agent.

Order past Teachers/Students isn't locked — later modules may need to slot in earlier if a dependency turns out tighter than expected. This already happened once: Attendance turned out to need Academic Terms as a real module (not a column), and Terms turned out to need Students' class assignment to become session-scoped rather than a fixed FK — so that migration got pulled forward ahead of Attendance instead of being deferred.

## Modules and how they relate

Everything hangs off `School` (the tenant, already built in the Ministry module). Nothing here is an independent silo — each module is a node with real foreign-key edges to the others:

- **Teachers** — belong to a School. **Not** linking Teachers to Classes yet (see Standing decisions) — for now Teachers stands alone. (`App\Models\Teacher`, `/teachers`)
- **Classes** — belong to a School. Have many Students. **Not** linking to Teachers yet (see Standing decisions). Modeled as `App\Models\SchoolClass` / table `school_classes` since `Class` is a reserved word in PHP; routes and UI still say "Classes" (`/classes`).
- **Students** — belong to a School. Class placement is now a session-scoped `Enrollment` (`student_id` + `academic_session_id`, unique per pair) rather than a fixed `class_id` FK — see below. Carry their own nullable `email`/`phone` (confirmed: students get contact fields independently of Guardians, not instead of them — Guardians will get their own contact info too when that module is built) and a nullable `admission_date`. Have one or more Guardians (many-to-many — siblings share a guardian, a guardian can have multiple children at the school). Will have Attendance records and Academic records, scoped by term. Supports CSV export/import via `maatwebsite/excel` (`App\Exports\StudentsExport`, `App\Imports\StudentsImport`) — import matches the `class` column to an existing class by name (case-insensitive) within the acting school, resolves it against the school's current session, and silently skips rows if the class doesn't match or no current term is set. (`App\Models\Student`, `/students`, `/students/export`, `/students/import`)
- **Guardians** — linked to Students many-to-many via `guardian_student` pivot (not a login account — see below). Pivot carries `relationship` (father/mother/guardian/other) and `is_primary`. **Simplification**: a guardian's relationship type and primary-contact flag are uniform across all of their linked children in one save (the edit form does a full `sync()`, not per-child editing) — a guardian who is "Mother" to one child and something else to another isn't supported yet. Only one guardian can be primary per student — marking a new guardian primary for a student automatically unmarks any other guardian's primary flag for that same student. Supports CSV export/import like Students (`App\Exports\GuardiansExport`, `App\Imports\GuardiansImport`) — import resolves a `Children` column formatted as `Name (AdmissionNumber); Name (AdmissionNumber)` against the school's students by admission number, skipping rows where nothing resolves. Both Students and Guardians exports cross-reference each other (Student export lists guardians with relationship; Guardian export lists children with admission number). (`App\Models\Guardian`, `/guardians`, `/guardians/export`, `/guardians/import`)
- **Academic Sessions & Terms** — foundational module that other modules scope their data by. An `AcademicSession` ("2025/2026") belongs to a School and has many `AcademicTerm`s (First/Second/Third Term). Exactly one Term is `is_current` per school at a time (same one-active-per-scope pattern as Guardian `is_primary`) — this is what UI defaults new Attendance/Academic entries to, and is the hook for eventually gating entry into closed terms. A Student's class placement becomes a session-scoped `Enrollment` (student_id, school_class_id, academic_session_id — one class per student per session), replacing `Student.class_id`. See "Academic Sessions & Terms — design notes" below for the full shape and open questions. (Not yet built.)
- **Attendance** — **done.** One row per student per date (`App\Models\Attendance`; unique on `student_id`+`date`), capturing `school_class_id` and `academic_term_id` at the time attendance was taken (resolved from the student's current-session Enrollment, not derived live — so history stays correct even after a student changes class later). `AttendanceStatus` enum: Present/Absent/Late/Excused. Single page (`GET`/`POST /attendance`, nav "Attendance"): pick a class + date, the roster loads from that class's current-session enrollments, mark each student, one bulk save (`updateOrCreate` per student, so resaving the same date corrects rather than duplicates). Requires a current academic term to exist (same `class_id`-attached validation error pattern as Students) and the date must fall within that term's range. No edit/destroy of individual records — correcting a day is just resaving it. Tests: `AttendanceControllerTest`.
- **Academics** — **done.** Two pieces: `Subject` (`App\Models\Subject`, `/subjects`) is a simple school-scoped list (name only), CRUD like Classes. `Teacher.subjects` was originally a free-text JSON array disconnected from this list — **reconciled** in the detail/show-pages initiative below (step 9): it's now a real `BelongsToMany` to `Subject` via a `subject_teacher` pivot, so "what a teacher is qualified to teach" and "the school's gradeable-subject list" are the same data, not two drifting copies. `Grade` (`App\Models\Grade`, `/grades`) is one row per student per subject per term (unique on `student_id`+`subject_id`+`academic_term_id`), capturing `school_class_id` and `academic_term_id` at save time the same way Attendance does. `ca_score` (0–40) and `exam_score` (0–60) are the only inputs; `total` and the `GradeLetter` (A/B/C/D/F, thresholds: 70/60/50/40) are derived on every save via a model `saving` event, never entered directly, so they can't drift out of sync. `teacher_id` is optional, free-picked per save (not a standing Subject↔Teacher assignment). Same page shape as Attendance: pick a class + subject, roster loads from current-session enrollments, bulk save (`updateOrCreate` per student, per subject+term). Requires a current academic term (same pattern as Students/Attendance). Tests: `SubjectControllerTest`, `GradeControllerTest`.
- **Finance & Expenses** — belongs to School only. **Confirmed scope: outgoing costs only** (these are public schools — no tuition/fees collected from families, so no student/guardian billing). Leaving room in the design to add an income/fees side later if that ever changes, but not building it now. Likely scoped by Session (a budget/expense period), not Term.
- **Reports** — scope not decided yet. Could mean academic report cards (per student/term) or Ministry-facing analytics (what the AI assistant queries), or both — these are different consumers of the same underlying data, not necessarily one module. Deciding when we get there, same as Dashboard.
- **Dashboard** — last. A summary view over whichever modules exist by the time we build it.

## Academic Sessions & Terms — design notes

**Status: built.** `App\Models\AcademicSession`, `App\Models\AcademicTerm`, `App\Enums\TermName`. Routes: `academic-sessions` resource (index/store/update/destroy) plus nested `academic-terms` routes (`POST academic-sessions/{session}/terms`, `PUT`/`DELETE academic-terms/{term}`, `POST academic-terms/{term}/current` to flip the current flag). Frontend: `school/academic-terms/index.tsx`, nav item "Academic Terms". Tests: `AcademicSessionControllerTest`, `AcademicTermControllerTest`. Term naming was hardcoded to the `TermName` enum (First/Second/Third Term) per the standing decision below — the "confirm no school needs a different structure" open question was accepted as a risk for now rather than blocking the build.

**Models:**
- `AcademicSession` — `school_id`, `name` (e.g. "2025/2026"), `start_date`, `end_date`. Has many `AcademicTerm`, has many `Enrollment`. No `is_current` flag of its own (see below) — a session is "current" only in the derived sense that it contains the current term.
- `AcademicTerm` — `school_id` (denormalized for scoping queries without a join), `academic_session_id`, `name` (enum: FirstTerm/SecondTerm/ThirdTerm), `start_date`, `end_date`, `is_current` (bool; single-current-per-school enforced at the controller level — same pattern as Guardian's primary-flag flip — not a DB constraint). Attendance and Academic records will reference `academic_term_id` directly (not session — session is reachable via the term).
- `Enrollment` — `school_id`, `student_id`, `school_class_id`, `academic_session_id`. Unique on (`student_id`, `academic_session_id`) — a student has exactly one class per session. Replaces `Student.class_id`.

**Status: Students migration built.** `students.class_id` dropped; `Enrollment` (`App\Models\Enrollment`) is the new source of truth. `StudentController@store`/`update` resolve the school's current term (`AcademicTerm::where('is_current', true)`) and create/`updateOrCreate` an Enrollment for that session — the `class_id` field name is unchanged on the form, so the UI didn't need reshaping beyond making the displayed class nullable. **Both Store/UpdateStudentRequest now require a current academic term to exist** (validation error surfaces on `class_id`: "Set a current academic term before adding students.") — a school must set up at least one term before it can add or reassign students. The Students index page shows a dismissible-free notice + disables "Add Student" when no current term is set, linking to Academic Terms. `StudentsImport` switched from `ToModel` to `OnEachRow` (matching `GuardiansImport`'s pattern) so it can create the Enrollment alongside the Student; it silently skips every row if there's no current term. `SchoolClass::students()` relation was removed (nothing referenced it, and a class no longer has a single well-defined "students" list without specifying a session).

**Promotion is manual, one student (or row) at a time** — editing a student's class while a new session is current creates a *new* Enrollment for that session, leaving prior sessions' Enrollments untouched as history. There's no bulk "promote everyone to the next class" action yet.

**Remaining open questions:**
- What happens to Attendance/Academic data when a term is closed and a new one made current — is old data still editable, or locked? (Moot until Attendance exists.)
- A bulk promotion action (advance a whole class to the next session at once) may be worth adding once schools have more than a session or two of history — not built, since per-student reassignment via the existing Edit form covers it for now.
- Term naming: fixed enum (First/Second/Third Term) is the Nigerian public-school norm this app targets — confirm no school on the platform uses a different term count/structure before this becomes a real constraint.

## Detail/show pages initiative — audit & plan (2026-09-17)

**Audit finding: every module (Teachers, Classes, Students, Guardians, Attendance, Grades, Subjects, Academic Terms) is index-only.** All resource routes are registered `->only(['index','store','update','destroy'])` (`routes/web.php:24-66`) — create/edit is a modal on the index page, and there is no `show` route, controller method, or detail page anywhere in the school portal. Concretely: no click-through from a class to its roster, from a student to their attendance/grades/guardians, or from a teacher to their assigned classes. Fixing this is now its own initiative, phased below since several show pages need relations (and one schema addition) that don't exist yet.

**Other gaps found in the same audit, independent of show pages:**
- `Student` has no `attendances()`/`grades()` relation despite the FK columns existing; `SchoolClass` has no `enrollments()`/`students()`/`attendances()`/`grades()` (its `students()` was actually removed when class placement moved to `Enrollment` — see above); `Teacher` has no `grades()`; `Subject` has no `grades()`; `School` is missing `students()`/`guardians()`/`enrollments()` even though it declares hasMany for everything else.
- ~~`GuardianController::index()` only surfaces the *first* linked student's `relationship`/`is_primary` pivot values per row~~ — re-examined while building the show page: this isn't actually a bug. Per the standing "Simplification" decision above, `syncStudents()` (and `GuardiansImport`) always write the *same* `relationship`/`is_primary` to every one of a guardian's linked students in a single save — so the pivot is uniform across all of a guardian's children by construction, and reading the first one is always correct today. Flagged in error by the initial audit, which hadn't cross-referenced this file's own documented decision.
- Ministry `School.activated_at` is fillable/cast but never selected/exposed by `SchoolController::index()` — display gap for an existing column.
- Ministry Schools module has no show/edit/destroy at all (`routes/web.php:24`, `only(['index','store'])`) — can't view a school's detail, resend an invitation, or deactivate one.

**Decision made:** Teacher↔Class assignment (deferred earlier, see Standing decisions) is now unblocked since Academic Terms exists. Shape: **one class teacher per class per academic term** (Nigerian "form teacher" norm) — a simple assignment table (`school_class_id`, `teacher_id`, `academic_term_id`), not per-subject. Subject-specific teaching stays as-is, loosely via `Grade.teacher_id`.

**Phased plan:**

1. ✅ **Relation groundwork** (no schema change) — added the missing Eloquent relations listed above (`Student::attendances()/grades()`, `SchoolClass::enrollments()/attendances()/grades()/teacherAssignments()`, `Teacher::grades()/classAssignments()`, `Subject::grades()`, `School::students()/guardians()/enrollments()`). `SchoolClass` deliberately still has no plain `students()` — a class has no well-defined roster without specifying a session, same reasoning as when it was originally removed; show pages resolve the current-session roster explicitly via `Enrollment`, as Attendance/Grades already did.
2. ✅ **Class↔Teacher assignment** — new `class_teacher_assignments` table + `App\Models\ClassTeacherAssignment` (`school_class_id`, `teacher_id`, `academic_term_id`, unique per class+term — one class teacher per term, per the "form teacher" norm decided over the deferred standing decision). `ClassTeacherAssignmentController@store` resolves the school's current term server-side (same pattern as Attendance/Grades) and `updateOrCreate`s the assignment; `@destroy` unassigns. Routes: `POST`/`DELETE classes/{class}/teacher`. Tests: `ClassTeacherAssignmentControllerTest`.
3. ✅ **Class show page** — `GET /classes/{class}` (`SchoolClassController@show`, `school/classes/show.tsx`): roster (current-session enrollments → students) with each student's current-term attendance breakdown (present/absent/late/excused), the current-term class teacher (with an assign/change/remove dialog), and class-wide stats (students enrolled, attendance rate). Grade summary intentionally deferred — a per-student "average score" isn't well-defined across unrelated subjects without a report-card view, which is Student show's job (step 4). Classes index now links each row to its show page. Tests: extended `SchoolClassControllerTest`.
4. ✅ **Student show page** — `GET /students/{student}` (`StudentController@show`, `school/students/show.tsx`): profile fields, current class (resolved from the current-term enrollment), full enrollment history across sessions, guardians with this student's own pivot values (no ambiguity here since each guardian's pivot is already scoped to this one student — the multi-child pivot bug is specific to `GuardianController::index`'s list row, still queued for step 6), attendance history grouped by term (present/absent/late/excused counts + rate), and grades grouped by term (per-subject CA/exam/total/grade + term average) — the report-card view step 3 explicitly deferred. Students index now links each row to its show page. **Found and fixed in passing:** adding `show` to the `students` resource meant `GET /students/{student}` would greedily match `students/export` as a student ID — moved the `export`/`import` routes before the resource registration (same latent conflict will need the same fix for `guardians` in step 6). Tests: extended `StudentControllerTest`.
5. ✅ **Teacher show page** — `GET /teachers/{teacher}` (`TeacherController@show`, `school/teachers/show.tsx`): free-text subjects list, class assignments across all terms (from step 2's `ClassTeacherAssignment`, current term flagged and linking to that class's show page), and grades they've entered grouped by term then by subject+class (students graded count + average) — reuses `Teacher::grades()` and `Teacher::classAssignments()` from step 1. Teachers index now links each row to its show page. Tests: extended `TeacherControllerTest`.
6. ✅ **Guardian show page** — `GET /guardians/{guardian}` (`GuardianController@show`, `school/guardians/show.tsx`): profile, and every linked student with their own relationship/primary badge (linking out to each student's show page) — kept per-student rather than assuming uniformity, so the page stays correct even if the "same value for all children" simplification is ever relaxed. Guardians index now links each row to its show page. **Same routing fix as step 4:** `guardians/export`/`guardians/import` moved ahead of the resource registration before adding `show`, for the same `{guardian}` route-greediness reason. Tests: extended `GuardianControllerTest`.
7. ✅ **Attendance & Grades history views** — the per-student history (attendance-by-term, grades-by-term) landed as part of steps 3–4 already. This step closes the remaining class-level gap that step 3 explicitly deferred: `SchoolClassController@show` now also returns `grade_summary` (current term, grouped by subject: students graded, class average, passing count) and `attendance_trend` (last 14 recorded days for the current term: present/absent/late/excused per day) — both rendered as new cards on `school/classes/show.tsx`. Roster rows there now also link out to each student's show page, closing the loop between Class → Student. Tests: extended `SchoolClassControllerTest`.
8. ✅ **Ministry Schools** — `GET /ministry/schools/{school}` (`SchoolController@show`, `schools/show.tsx`): profile (invited/activated dates, who invited them), latest invitation status (pending/accepted/expired, with a "Resend Invitation" action gated to `status === invited`), and usage stats (teacher/class/student counts). Plus two new actions: `POST schools/{school}/suspend` and `.../reactivate`, gated by current status (`abort_if`/`abort_unless` 403 on an invalid transition — schools index links each row to its show page.
   - **Found and fixed a real functional gap, not just a display one:** `SchoolStatus::Suspended` already existed in the enum and was counted in the index stats, but nothing anywhere ever set it or acted on it — suspending a school would have been cosmetic-only. Added the enforcement side: `SchoolLoginRequest::authenticate()` now logs a school user back out and fails auth if their school's status is `Suspended`, checked *after* a successful credential match (so it doesn't leak account existence). Tested in `SchoolAuthenticationTest`.
   - **Found and fixed a second gap while wiring the stats:** `School::teachers()/classes()/students()` all resolve through models using `BelongsToSchool`, whose global scope reads the *`auth:school`* guard — which is never authenticated in the Ministry portal (a `MinistryUser`, not a `SchoolUser`, is logged in there). Without a fix, every one of those relation queries would have silently returned zero from Ministry-side code, no matter how much data the school actually has. Fixed by querying with `->withoutGlobalScopes()` in `SchoolController@show`, the same pattern the test suite already uses to inspect other schools' data. This is a standing trap worth remembering for any *future* Ministry-side code that touches school-scoped models.
   - `activated_at` now flows through on the show page (index still omits it — it's a one-off ministry detail view, not needed in the list).
   - Tests: extended `SchoolControllerTest`.
9. ✅ **Subject show page + Teacher↔Subject reconciliation** — resolved together since the show page's "which teachers teach this" needed a real relation to be trustworthy. Decision (confirmed with the user, same as step 2's Class↔Teacher call): migrate `Teacher.subjects` from a free-text JSON array to a real `subject_teacher` many-to-many pivot against the school's canonical `Subject` list.
   - Migrations: `create_subject_teacher_table` (pivot, unique per subject+teacher), then `migrate_teacher_subjects_to_pivot_and_drop_column` — a genuine **data** migration, not just schema: for every teacher's existing free-text array, it resolves or creates a matching `Subject` per school (case-insensitive name match) and links it via the pivot, before dropping `teachers.subjects`. `down()` reverses both the schema and the data (rebuilds the JSON array from the pivot). ## Standing decisions

- **`school_users` vs. Teacher/Guardian records — kept separate** (established in the accept-invitation work): `school_users` are platform *login accounts*. Teachers and Guardians are *data records* the school manages — most will never have a login. If a teacher or guardian ever needs portal access themselves, that's a distinct future decision, not the default.
- **No student billing** — Finance & Expenses is expense-tracking only, per public-school context above.
- ~~Teacher ↔ Class assignment deferred~~ — **resolved** in the detail/show-pages initiative below (step 2), once Academic Terms existed to model it against: one class teacher per class per term, via `ClassTeacherAssignment`.
- **Academic Sessions & Terms is a real module, not a column** — confirmed after Attendance's dependency on it surfaced the need. Session → Terms hierarchy (Nigerian public-school "First/Second/Third Term" structure), with a single `is_current` term per school. Student-class assignment moves from a fixed `Student.class_id` FK to a session-scoped `Enrollment`, so promotion history is preserved. See "Academic Sessions & Terms — design notes" above for the full shape.
